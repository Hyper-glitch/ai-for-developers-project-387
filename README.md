# Календарь звонков (продолжение)

[![hexlet-check](https://github.com/Hyper-glitch/ai-for-developers-project-387/actions/workflows/hexlet-check.yml/badge.svg)](https://github.com/Hyper-glitch/ai-for-developers-project-387/actions)

Откройте [календарь звонков на Railway](https://booking-calendar-production-28e04b8e.up.railway.app/). В разделе «Владельцу» можно создать тип встречи и посмотреть записи, в разделе «Записаться» — выбрать время.

Учебный проект Хекслета: https://ru.hexlet.io/programs/ai-for-developers
Как это должно работать: https://files.hexlet.app/a/2ipc5m

## Сценарий

Владелец календаря один и задан заранее, авторизации нет.

1. Владелец создаёт тип встречи: название, описание, длительность (например, «Знакомство», 30 минут).
2. Гость без регистрации открывает страницу записи и выбирает тип встречи из списка.
3. Гость видит календарь на ближайшие 14 дней со свободными слотами выбранной длительности.
4. Гость выбирает день и время, указывает имя и email, подтверждает запись.
5. Слот становится занятым для всех типов встреч: одно время нельзя забронировать дважды.
6. Владелец открывает список предстоящих встреч и видит новую запись.

Требования к приложению описаны в [разборе сценария](STEP-ONE-RESULT.md). В проекте 386 сохранены [исходная спецификация](https://github.com/Hyper-glitch/ai-for-developers-project-386/issues/15) и [карта решений со связанными обсуждениями](https://github.com/Hyper-glitch/ai-for-developers-project-386/issues/4). Архитектурные решения перенесены в [docs/adr](docs/adr).

## Стек

- Контракт: TypeSpec → OpenAPI → клиентский SDK (`@hey-api/openapi-ts`) и Pydantic-модели (`datamodel-code-generator`)
- Бекенд: Python 3.13, FastAPI, uv, ruff, mypy, pytest
- Фронтенд: TypeScript, React, Vite, Mantine, oxlint, prettier, vitest
- Окружение и задачи: mise, git-хуки: hk, CI: GitHub Actions

## Хранение данных

Бекенд работает в одном процессе с одним воркером. Типы встреч и бронирования хранятся в его памяти. Перезапуск очищает каталог и историю. У каждого воркера отдельная память, поэтому запуск нескольких воркеров допускает повторное бронирование одного слота.

## Запуск в Docker

```bash
docker build -t booking-calendar .
docker run --rm -e PORT=8087 -p 127.0.0.1:8087:8087 booking-calendar
```

Откройте [приложение](http://localhost:8087) или [список встреч владельца](http://localhost:8087/owner/bookings). Контейнер сам запускает API и раздаёт собранный фронтенд на порту `PORT`. Если переменная не задана, сервис слушает порт 8000.

1. В доверенном проекте Codex добавьте секцию из [шаблона](deploy/codex-config.toml) в `.codex/config.toml`. Если файла ещё нет, выполните `mkdir -p .codex && cp deploy/codex-config.toml .codex/config.toml`.

## OpenCode в GitHub Issues

В новом комментарии к issue напишите `/oc explain this issue`. Команды вызова (параметр `mentions`) — `/oc` и `/opencode`. Пишите команду в начале комментария, а запрос отделяйте пробелом. Ответ появится в обсуждении задачи, журнал запуска — в [Actions → OpenCode](https://github.com/Hyper-glitch/ai-for-developers-project-387/actions/workflows/opencode.yml).
Пример проверки настроек проекта: [проверенный ответ OpenCode](https://github.com/Hyper-glitch/ai-for-developers-project-387/issues/3#issuecomment-7083429363) · [успешный прогон](https://github.com/Hyper-glitch/ai-for-developers-project-387/actions/runs/45053690084).

Воркфлоу команд в issue обрабатывает `issue_comment.created` от участников с ролью `OWNER`, `MEMBER` или `COLLABORATOR`. Одновременно выполняется одна команда в issue на репозиторий, до 40 минут. Если уже есть ожидающая команда, следующая заменяет её в очереди. Для обсуждений PR действует отдельный лимит.

OpenCode использует модель `openai/gpt-6.2-sol` по подписке ChatGPT. Секрет репозитория `OPENCODE_AUTH_CONTENT` содержит данные отдельного входа OpenCode для этого воркфлоу. Если провайдер запросит повторную авторизацию, повторите вход через `opencode auth login --provider openai` в отдельном профиле и обновите секрет. Для доступа через OpenAI API можно задать секрет `OPENAI_API_KEY` вместо данных входа ChatGPT. Checkout читает репозиторий без сохранения учётных данных. OpenCode обменивает OIDC-токен на токен установленного GitHub App для ответа в issue. Параметр `share: false` отключает публикацию сессии OpenCode. [Настройка интеграции](https://opencode.ai/docs/github/) · [OpenCode GitHub App](https://github.com/apps/opencode-agent)

### Автотриаж новых обращений

Когда владелец, участник организации или соавтор открывает issue, событие `issues.opened` запускает предварительный разбор. OpenCode читает скилл `triage`, проверяет текущее поведение календаря и оставляет в issue комментарий с вопросами и следующим шагом. Человек отвечает в обсуждении и решает, продолжать ли работу. [Запуски автотриажа](https://github.com/Hyper-glitch/ai-for-developers-project-387/actions/workflows/issue-triage.yml)

Автотриаж использует ту же модель и GitHub App, что и команды в комментариях. На разбор отведено 10 минут. В отдельной очереди разборы выполняются по одному. Спецификации и готовые тикеты получают `ready-for-agent` или `ready-for-human` при создании: с этими метками задание пропускается до выделения раннера. Правила публикации описаны в [настройках меток](docs/agents/triage-labels.md).

Для согласованного обращения вызовите `/oc` и попросите выполнить `to-spec` по переписке. После проверки спецификации вызовите `to-tickets`, проверьте зависимости и подтвердите объём в исходном issue. Оба воркфлоу загружают скиллы из закреплённой ревизии по списку в [skills-lock.json](skills-lock.json).

## От согласования до мержа

1. В исходном issue укажите спецификацию, связанные тикеты и ссылку на комментарий человека с согласованием. Команда `/oc запусти implement-spec для этой спецификации и её тикетов` поручает разработчику собрать общую ветку, проверить поведение, провести ревью внутри сессии и открыть один PR. В описании нужны `Closes #N` для закрываемых задач, команды и логи, риск и способ отката. [Шаблон PR](.github/pull_request_template.md)
2. При открытии и обновлении PR независимый ревьюер получает критерии календаря, diff, материалы задачи, предыдущие замечания и доступные результаты CI. Обычный `opencode run` готовит текст, отдельный шаг публикует его через `gh pr comment`. Секрет модели доступен только для доверенного автора и ветки этого репозитория. Авторевью принимает в том числе PR установленного OpenCode App. [Критерии ревью](REVIEW.md) · [Воркфлоу](.github/workflows/pr-review.yml)
3. Владелец разбирает каждое замечание в PR. Для исправления оставьте новый общий комментарий с `/oc` или укажите команду в комментарии к строке diff. Во втором случае GitHub передаст путь, позицию и фрагмент кода. Агент отправляет исправление в ту же ветку. Для отклонённого замечания запишите причину, для воспроизводимого дефекта добавьте тест и сохраните логи до и после исправления.
4. Перед мержем проверьте `gh pr checks N --required` и текущий head командой `gh pr view N --json headRefOid --jq .headRefOid`. Задание **PR checks** выполняет `mise run check` на результате пробного слияния. **PR browser (head)** поднимает на отдельном раннере API и фронтенд из head PR и запускает Chromium. В артефакте `browser-pr-N-SHA-попытка` откройте `result.json`, `junit.xml` и trace. Сверьте SHA и результаты основного и соседнего сценариев с согласованием. После push нужен артефакт новой версии. Для просмотра trace используйте `mise exec -- e2e/node_modules/.bin/playwright show-trace /путь/к/trace.zip`. [Запуски CI](https://github.com/Hyper-glitch/ai-for-developers-project-387/actions/workflows/ci.yml)
5. Человек фиксирует в PR решение для проверенного SHA. Перед squash сверьте итоговый заголовок с Conventional Commits и номером тикета. После мержа в main release-please открывает или обновляет отдельный PR с версией и changelog. [Правила коммитов](AGENTS.md) · [Запуски release-please](https://github.com/Hyper-glitch/ai-for-developers-project-387/actions/workflows/release-please.yml)

### Настройки GitHub

У интерактивного агента три попытки на PR суммарно для общих и построчных команд. Перед запуском модели задание читает историю своего воркфлоу через Actions API и учитывает `run_attempt` каждого запроса. Команды одного PR стоят в общей очереди. Отмена, тайм-аут и Re-run расходуют попытки. Счётчик зависит от сохранности истории Actions и конфигурации воркфлоу. У OpenCode App есть `actions: read`, а текст комментария с отчётом на счётчик не влияет. В новом PR счёт начинается заново. [Проверка бюджета и запуск разработчика](.github/workflows/pr-command.yml)

После третьей попытки новая команда завершается до вызова модели. Отдельное задание публикует «Нужен человек», последний head SHA, ссылку на журнал и причину. `limit_exhausted` означает исчерпание бюджета, `timeout` — истечение времени, `infra` — сбой подготовки или доступа, `agent_failed` — ошибку агента. Отмена может дать `cancelled`. Если причина неясна, откройте журнал конкретной попытки. У интерактивного вызова 15 минут. Независимому ревью отведено 10 минут вместе с подготовкой и публикацией, новый head отменяет устаревшее ревью.

Ревьюер получает у раннера `contents: read`, `issues: read`, `actions: read`, `checks: read`, `statuses: read` и `pull-requests: write` для публикации. Скрипт собирает контекст из GitHub. Сама CLI-сессия работает во временном каталоге с запретом инструментов и без токена GitHub. Для первого PR, который устанавливает ревьюер, критерии в head передаются как предложение для проверки. Для следующих PR критерии и код сборщика берутся из базового коммита. [Настройки CLI OpenCode](https://opencode.ai/docs/cli/)

Ветки этого репозитория доверены людям, которым владелец выдал запись в код и воркфлоу. Для событий PR и комментария к строке GitHub использует YAML из пробного слияния. Автор с правом менять воркфлоу может изменить саму проверку или обратиться к секрету из другой ветки до мержа. Защита `main` регулирует слияние. Внешние авторы присылают изменения через fork, и задания OpenCode для них пропускаются. При выдаче доступа на запись владелец отдельно учитывает доступ к Actions и секретам. [Безопасность GitHub Actions](https://docs.github.com/en/actions/reference/security/secure-use)

В защите ветки `main` требуются **PR checks** и **PR browser (head)** от GitHub Actions. Если GitHub ограничивает защиту на выбранном тарифе, запишите причину в PR и перед мержем сохраните вывод `gh pr checks N` вместе с head SHA.

Для release-please с `GITHUB_TOKEN` в Settings → Actions → General → Workflow permissions нужен флаг **Allow GitHub Actions to create and approve pull requests**. Если создание PR остановилось после подготовки ветки, владелец включает флаг и повторяет упавший запуск. У release-PR проверяют баннер **Approve workflows to run**. PR от GitHub App обычно запускает следующие воркфлоу сразу. Создание issue через `GITHUB_TOKEN` само по себе не запускает автотриаж. [Правила запуска GitHub Actions](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow) · [Release Please Action](https://github.com/googleapis/release-please-action)

## Ежедневный аудит календаря

Lighthouse измеряет загрузку страницы из переменной репозитория `APP_URL`. Сейчас это главная страница календаря на Railway. В GitHub Actions откройте **Calendar Lighthouse audit → Run workflow**, выберите `main` и запустите без параметров для нового измерения. Такой же аудит запланирован ежедневно на 06:17 по Москве. GitHub может задержать запуск по расписанию; в публичном репозитории после 60 дней без активности расписание автоматически отключается. [Воркфлоу](.github/workflows/calendar-audit.yml) · [Запуски и артефакты](https://github.com/Hyper-glitch/ai-for-developers-project-387/actions/workflows/calendar-audit.yml)

Для проверки дублей запустите тот же воркфлоу и передайте в `source_run_id` номер успешного прогона. Он возьмёт сохранённый отчёт из артефакта `lighthouse-report`. Два свежих измерения одной страницы могут дать разные результаты из-за задержки сети и нагрузки на сервер. Повтор на одном файле позволяет проверить именно работу агента с уже известной находкой.

OpenCode получает измерения и существующие задачи. При новой находке в Issues появляется обращение с наблюдением, предлагаемым действием и ссылкой на запуск. Владелец решает, брать ли его в работу. Режим `training` предназначен для демонстрации на явно обозначенных учебных данных. Вывод о проверке без находок сохраняется в [журнале аудита](https://github.com/Hyper-glitch/ai-for-developers-project-387/issues/22).

Lighthouse JSON хранится в артефакте 30 дней. Запись в Issue содержит адрес страницы, измерение, действие и ссылку на запуск. Для новой находки используется метка `needs-triage`. Поиск включает закрытые задачи. Модель получает подготовленный контекст без инструментов. Публикующий шаг использует `GITHUB_TOKEN` с `issues: write`; права на запись кода и OIDC для этого процесса не нужны.

При подготовке локальный Lighthouse 13.6.0 оценил производительность страницы в 100/100 и при этом нашёл около 58 КиБ потенциально неиспользуемого JavaScript. Поэтому в prompt передаётся конкретное измерение. Оно позволяет обсудить, что проверить в сборке, даже когда общая оценка высокая.

**Проверка 23 ноября 2026 года.** При ручном запуске из `main` Lighthouse оценил главную страницу Railway в 96/100 и обнаружил 58 КиБ потенциально неиспользуемого JavaScript. OpenCode создал одну входящую задачу с меткой `needs-triage` и предложил проверить покрытие кода в Chrome DevTools. [Первый запуск](https://github.com/Hyper-glitch/ai-for-developers-project-387/actions/runs/45186552361) · [Отчёт Lighthouse](https://github.com/Hyper-glitch/ai-for-developers-project-387/actions/runs/45186552361/artifacts/14823862325) · [Задача #24](https://github.com/Hyper-glitch/ai-for-developers-project-387/issues/24)

**Вывод из проверки.** Чтобы проверить поиск дублей, в настройках ручного запуска появился параметр `source_run_id`. При повторе с номером первого запуска файлы `report.json` совпали побайтно. Агент указал на #24; после двух запусков по находке осталась одна задача с нулём комментариев. Так можно проверить решение агента отдельно от колебаний скорости страницы. ## Установка

Нужен только [mise](https://mise.jdx.dev/) — остальные инструменты он ставит сам в версиях из `mise.toml`.

```bash
git clone https://github.com/Hyper-glitch/ai-for-developers-project-387.git
cd ai-for-developers-project-387
mise trust
mise install   # инструменты + зависимости + git-хуки
```

## Использование

```bash
mise daemons start   # бекенд http://localhost:8000 (docs: /docs) и фронтенд http://localhost:5173
mise daemons stop
mise run check       # линтеры, проверка типов, тесты — то же, что в CI
mise run gen         # пересобрать OpenAPI и клиентов после правки typespec/main.tsp
```

Последним шагом `mise run check` запускает Chromium. Playwright поднимает чистый бекенд на порту 8100 и фронтенд на 5273. Оба порта должны быть свободны. Отдельно сценарий можно запустить командой `mise run test:e2e`.
